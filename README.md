# FullStacked onboarding

The first-launch experience of the [FullStacked](https://fullstacked.org) app. It shows that FullStacked is a real JavaScript runtime on the device by building the [demo](https://github.com/fullstackedorg/demo) live: `git clone`, `npm install` and an esbuild bundle, with progress, on the device itself. No server, no account.

The whole onboarding plays on a deep navy stage with the FullStacked world, a particle animation (plain WebGL, `src/world/`, no dependency). While it is up, it paints the page (`<html>`, `<body>` and `theme-color`) with the stage's top colour, so the status bar the native shells draw from the page matches it; the page gets its own colours back when the onboarding leaves. The words stay short, catchy and non-technical: one line per screen, no exact numbers. The top left shows the FullStacked mark (monochrome, quiet), a link to fullstacked.org. Every screen has the same bar at the bottom: _Show details_ on the left (once the build has started) and _Next →_ on the right. Nothing moves on by itself: each step waits for _Next_, which stays disabled until the step is done. On a keyboard, → and Enter are _Next_ and Escape is _Skip_.

1. **Welcome**: the world turning, _Welcome to FullStacked_, the tagline from fullstacked.org (_Build anything. Run it everywhere._) and one line (_Whole projects, built and running right here. No server needed._). _Run the demo →_ or _Skip_.
2. **Live build**: the world flies apart, then the real build makes it again. Clone the demo project from GitHub and check out the pinned commit (git objects stream in from the top left), install its packages (one cluster per package, labelled, from the top right), bundle it with the Tailwind CSS plugin (everything spirals into a core, with real lines of the project where the engine — Node.js — and the screen — the browser — meet in one file, `src/excerpt.ts`), then the core ignites into the world: the project runs. One short, non-technical line per step (_Gathering everything it needs to run._) and a thin four-part bar (download, install, build, run). _Show details_ unfolds a record of everything that happened so far, one section per step as it plays (its output, a check and a summary once done, the project's own lines under Build), kept for the whole build. On a fast device the build takes a second: the world replays what was recorded at a pace the eye can follow (each step at least 3 s, 4 s and 3.5 s), in the real order. A bar never stands still: while a step runs, time moves it toward 90 %, real progress faster, and only the real end completes it. A download or install with no sign of life for 90 s fails with _Try again_ instead of hanging.
3. **Ready**: _The demo project is ready_, a large _Explore the demo ↗_ capsule, in the grey of _Show details_ (it opens the demo project in a new window), _Show details_ (the build's record, still there) and _Finish →_. The demo project has its own file browser, so the onboarding shows no files. Before that, the build's numbers are written to `<demo>/user_data/build.json` for the demo project.
4. **Hand-over**: the config key `onboarding` is set to `"1"` and `onDone(stats)` is called.

A failed step says so in one sentence, opens the log, and offers _Try again →_ and _Continue_. Offline, the welcome screen offers _Continue →_ instead of the build. The words say "the demo project", never "app", and "this device" on every device.

## Quick start

```bash
npm install
npm start
```

`npm start` runs the onboarding on its own with the `fullstacked` CLI and opens it in your browser. `dev/` is its projects folder: the demo is cloned and built in `dev/demo` (ignored by git), and _Explore the demo_ opens it in another tab. Restart `npm start` after a change.

- `http://localhost:9000/?offline` behaves as if there was no network.
- `?dir=<name>` clones the demo to `dev/<name>` instead.
- `npm run build` only bundles; `npm run typecheck` runs `tsc`.
- Delete `dev/demo` to see a fresh clone again.

| `index.ts`            | The build plugin (`fullstacked --build -p <this repository> shell`)                     |
| `dev/index.ts`        | The standalone development page (`npm start`)                                           |
| `vendor/demo`         | The demo, as a git submodule at the pinned commit                                       |
| `scripts/pin-demo.ts` | Updates the pin                                                                         |

## API

```ts
import {
    startOnboarding,
    shouldRunOnboarding
} from "<onboarding>/src/index.ts";

if (await shouldRunOnboarding()) {
    const el = document.createElement("div");
    document.body.append(el);
    startOnboarding(el, {
        onDone: (stats) => {
            el.remove();
            openTerminal();
        },
        continueLabel: "Finish", // the last button, the default
        cloneDir: "demo" // default "demo", from the projects folder
    });
}
```

- `startOnboarding(el, options)` mounts the onboarding (a fixed, full-screen layer) in `el` and returns `{ done, unmount }`. `done` resolves with the stats given to `onDone`.
- `options.onDone(stats)` is the hand-over. It is called once, after `onboarding = "1"` is saved and the onboarding is removed: from _Skip_, from _Finish_ (after the build) or _Continue_ (after a failure, offline). `stats` is `{ outcome: "built" | "skipped" | "failed" | "offline", seconds, demoOpened, report?, error? }`, where `report` is what `build.json` holds.
- `shouldRunOnboarding()` is `true` while the config key `onboarding` (`fullstacked/config`, the context's `.git/config.json`) isn't `"1"`. In the app's shell, `config delete onboarding` brings the onboarding back on the next launch.

The demo goes to `cloneDir`. If that folder exists and is a clone of the demo, it is reused: reset, checked out at the pinned commit (fetched only if missing), reinstalled and rebundled. If it holds something else, the onboarding uses `demo-2`, `demo-3`… and never touches it.

## The pinned demo

The onboarding clones `https://github.com/fullstackedorg/demo.git`, then checks out `DEMO_COMMIT` from `src/demo-pin.ts`, so changes on the demo's `main` never reach users before they are pinned here. The pin follows the `vendor/demo` submodule:

```bash
npm run pin-demo -- main        # move vendor/demo to the demo's latest main, stage it, regenerate src/demo-pin.ts
npm run pin-demo -- <tag|sha>   # or to a tag or a commit
npm run pin-demo                # regenerate src/demo-pin.ts from the commit recorded for vendor/demo
npm run pin-demo -- --check     # exit 1 if src/demo-pin.ts and vendor/demo disagree (CI)
```

Then commit `vendor/demo` and `src/demo-pin.ts` together. The script also measures the download shown on the welcome screen (the git pack and the npm tarballs of the lockfile). The pinned commit must be on a branch or tag of the demo's GitHub repository, or the runtime clone won't find it; the script warns otherwise. `src/demo-pin.ts` is committed, so building the onboarding needs neither git nor Node.

The submodule lives in `vendor/` so that it never collides with the runtime clone (`dev/demo` in development, `demo` in the app's projects folder). `npm start` doesn't need it: clone this repository without `--recursive` to work on the onboarding.

## In the app's shell

The app's shell (`shell/` in [fullstackedorg/fullstacked](https://github.com/fullstackedorg/fullstacked)) imports `./auto`, an empty module kept as a hook for build plugins. This repository's `index.ts` is such a plugin:

```bash
fullstacked --build -p plugins/onboarding shell
```

It intercepts `./auto` and adds two files to `shell/out`:

- `onboarding.js`, linked from `index.html` after the shell's bundle: a small loader without the runtime library. It sets `globalThis.fullstackedShell.held = true` at once, waits until the shell's runtime is ready, then imports `onboarding.mjs`.
- `onboarding.mjs`: `src/shell.ts` bundled with `bundleFile`. It reads the `onboarding` config key, then shows the onboarding (with _Open the terminal_) or opens the terminal right away. It runs in the shell's page and context (root: the projects folder), with no context of its own.

The onboarding bundle carries its own copy of the runtime library, as every bundle does. Every bundle of a page shares one bridge (`globalThis.fullstacked.__bridge`), so the shell's bundle and this one coexist.

### What the shell provides

The shell (`fullstackedorg/shell`, a submodule of `fullstackedorg/fullstacked`) holds the terminal until a startup plugin decides. `./auto` marks a bare start; when a plugin replaced it, the shell publishes these on `globalThis.fullstackedShell` and fires `fullstackedshell`:

| Hook                                     | What it does                                                                                                                                        |
| :--------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------- |
| `held`                                   | Set by the startup script as soon as it runs. Without it, the terminal opens after 3 s, so a script that failed to load never leaves a blank page.  |
| `openTerminal()`                         | Opens the terminal, or shows it again after `hideTerminal()`. Resolves with the same `{ terminal, shell, fitAddon, keyboard, element }` every time. |
| `hideTerminal()`                         | Hides the terminal (the shell fires `fullstackedshellhide`, and `fullstackedshellshow` when it is shown again).                                     |
| `registerCommand(command)`               | Adds a command, listed by `help` and completed by Tab. Returns a function that removes it.                                                          |
| `pauseDeeplinks()` / `resumeDeeplinks()` | Lets the plugin's own view handle deeplinks while it is shown.                                                                                      |

`docs/contributing/building.md` in `fullstackedorg/fullstacked` has the details.

Without a plugin, `./auto` is kept and the terminal opens as before. With one, the shell publishes `openTerminal` and the plugin's script decides. Only one plugin can intercept `./auto` in a build. Another shell plugin (a different hand-over, for example) reuses this one with its own startup module:

```ts
import { shellStartupPlugin } from "<onboarding>/index.ts";

export default shellStartupPlugin(
    new URL("./startup.ts", import.meta.url), // calls startOnboarding with its own onDone
    "startup"
);
```
